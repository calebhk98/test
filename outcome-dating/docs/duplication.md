# Duplication and divergence audit

An audit of duplicated or divergent logic across the codebase, read-only. Method: grepped for candidate duplication, then read both sides of every candidate and compared behavior at boundaries (null, empty, zero, max) rather than trusting text similarity.

## Fixed since the original audit

- **The trust-score exposure gate had two independent toggles; only one was wired in.** `shouldExposeRawTrustScore` (reading the documented `trust.expose_raw_score` config key) was never actually called by the live `GET /me/trust` route, which instead used a separate, unrelated feature flag. An admin toggling the documented control had zero effect. Fixed: `src/http/serializers/trust.ts#serializeTrustSummary` now calls `shouldExposeRawTrustScore` as its one gate.
- **The per-hour link rate limit ignored the trust-tier config it was supposed to track.** `message.service.ts#linkLimitForCaller` now delegates to `trust.service.ts#linksPerHourLimitFor` instead of re-deriving its own hardcoded `'limited'`-vs-everything-else boundary, so retuning `trust.link_min_level` now moves both the clickability gate and the send-time cap together.
- **A shared cursor helper exists** (`src/lib/cursor.ts`) and `message.service.ts` uses it. This closes the malformed-cursor 500-vs-400 inconsistency for that one endpoint, but **not** for `notification.service.ts`, `interest.service.ts`, `matches.service.ts`, or `timeline.service.ts`, which still each define their own local `decodeCursor` without the invalid-date check. See "still open" below.
- **The two parallel compatibility-scoring systems are consolidated.** `compatibility.service.ts` now calls `src/domain/questions/scoring.ts#aggregateQuestionScores` directly against the typed `question_bank`/`user_question_answers` tables; the old `questions`/`answers` tables and their separate scoring formula are gone (dropped in `db/migrations/022_drop_old_question_bank.sql`). There is exactly one scoring path today.

## Still open

- **Cursor validation gap, partial fix.** `notification.service.ts`, `interest.service.ts`, `matches.service.ts`, and `timeline.service.ts` still each carry their own `decodeCursor`; only `matches.service.ts`/`timeline.service.ts` validate the parsed date (`Number.isNaN` check), so a malformed cursor against notifications or interests still throws an unhandled `RangeError` deep in `pg` and surfaces as a 500 instead of a clean 400. Fix: point the remaining four call sites at `src/lib/cursor.ts`.
- **Offset pagination still used for three audit-trail-shaped lists.** `trust.service.ts#listMyTrustEvents`, `moderation.service.ts#listModerationActions`, and `venueSettlement.service.ts#listVenueSettlements` all use `OFFSET`-based pagination against tables background jobs write to continuously, which can silently skip or repeat a row across two page fetches if a row is inserted between them. The six other paginated services (ledger, notifications, matches, timeline, messages, interests) already use keyset pagination, which doesn't have this failure mode. Converting these three is a larger change (their `nextCursor` shape changes from a visible integer to an opaque cursor), so it wasn't done as part of the cursor-helper fix above.
- **The voucher expiry boundary is still the odd one out.** `voucher.service.ts`'s expiry sweep uses `expires_at < $1` (exclusive); interest and date-proposal expiry both use the inclusive convention (`<=`/`>=`). Low real-world impact (the window is one instant), but worth aligning the next time that file is touched.
- **`percentOfCents` is still duplicated, not extracted.** `dateProposal.service.ts#percentOfCents` and `venueSettlement.service.ts#computeVenuePayout` implement the same "round down, in the platform's favor" rule, cross-documented and currently in agreement, but not sharing an implementation. Worth extracting to `src/lib/money.ts` before a third money-rounding call site appears.
- **`filter.service.ts#haversineKm` and `distance.ts`'s internal `haversineKmExact` are still two independently-maintained copies of the same formula**, deliberately kept separate (filter enforcement is a different concern from privacy display), but with no test cross-checking that they agree. Worth a one-line regression test, not a merge.
- **Enumerations declared independently in TypeScript and SQL `CHECK` constraints remain unmechanized.** Every status-shaped column is declared twice (a `text` + `CHECK` in the migration, a string union in `domain/types.ts`), held together only by developer discipline. One pair has already drifted on purpose: `notification_preferences.category` and `notification_outbox.category` allow different value sets (the outbox adds `'safety'`, deliberately not user-configurable). A single test introspecting `information_schema.check_constraints` and asserting it matches the corresponding TypeScript union would turn a silent drift into a CI failure.
- **Test harness sprawl.** Nine near-identical DB-bootstrap files under `tests/unit/`, `tests/jobs/`, and `tests/http/` (roughly 1,400 lines combined) exist because each was built by a different concurrent agent. Verified safe today (each file uses a unique DB-prefix namespace and no file imports two harnesses), but genuinely repetitive. Deliberately deprioritized: these files are still each owned by different in-flight test suites, and merging them risks a wide-blast-radius conflict for low correctness benefit.

## Checked and found clean

Id generation (one `randomUUID()` wrapper, `src/lib/ids.ts`), the error hierarchy (one `AppError` tree), eligibility/filter evaluation (both discovery and interest-sending call the same `filter.service.ts#passesMutualFilters`, never a second copy), the privacy serializers (all explicit allowlists, no `{...spread}` anywhere), and the minimum-age check (dual-enforced in application code and a DB `CHECK`, both agreeing on every boundary checked, a legitimate defense-in-depth pattern rather than an accidental duplicate).

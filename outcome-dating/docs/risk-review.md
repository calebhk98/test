# Risk review: safety, legal, and product

An adversarial review of `SPEC.md`, cross-checked against `src/`. 48 findings originally, 11 critical. This pass re-verified every Top 10 item and the ones the README calls out as fixed; everything else keeps its original status unless marked otherwise. `mitigated` = code closes the gap, `partial` = reduces but doesn't close it, `open` = nothing addresses it, `n/a (design)` = a property of the spec's product design, not fixable by code.

A companion, spec-only review (not grounded in code) is folded in at the end: it raised the same money-in-dispute and zero-human-moderation concerns independently, before any of the code-level fixes below existed.

## Fixed since the original review

- **SAF-1, single-report instant suspension.** `moderation.service.ts#applyThresholds` now requires a corroboration model (`report.service.ts`, "SAF-1 FIX"): a `minor_suspected` report needs multiple independent, non-device-clustered credible reporters before it drives a suspension; an uncorroborated report gets a fast but reversible interim action instead. Verified in code and covered by an adversarial test (`tests/unit/safetyFixes.test.ts`, a sock-puppet brigade sharing IP/timing but distinct fingerprints still collapses to one corroborator).
- **SAF-2, distance trilateration.** Discovery and the profile page now share one bucketed, per-viewer-pair-jittered distance function (`domain/units/distance.ts#approximateDistanceBetween`); the old 1km/5km inconsistent, unjittered pair is gone. `tests/unit/distancePrivacy.test.ts` runs a real least-squares multilateration attack against it and asserts the recovered position misses by an order of magnitude worse than an unmitigated control.
- **PRIV-1, account deletion leaves sensitive data behind.** `deleteMyAccount` still needs verification of what it clears (**not re-checked in this pass** beyond the earlier fix note); treat as fixed only for the tables the deletion test (`tests/unit/deletion.test.ts`) actually reads row-by-row.
- **The trust-score exposure double-gate** (`docs/duplication.md` finding 1) is fixed: `shouldExposeRawTrustScore` is now the one gate `serializeTrustSummary` calls.
- **Production fake-adapter landmine (context for PAY-1/PAY-2 below).** The original review found no startup guard stopped a misconfigured production deployment from silently running on `FakeProcessor`, so escrow holds would "succeed," tickets would issue, and no real money would ever move, with a fully green reconciliation job because there was nothing to reconcile against. `src/config/adapters.ts#runProductionGuard` now refuses to start in `NODE_ENV=production` unless `PAYMENT_PROCESSOR=stripe` (with secrets), a real `MEDIA_MODERATION_PROVIDER` is registered, and `AUTH_TOKEN_SECRET`/`VOUCHER_QR_SECRET` are set to real values. This doesn't fix PAY-1/PAY-2 below (those are still open legal questions), it just makes the failure loud instead of silent.

## What the spec gets right (keep these)

Mutual hard filters that the algorithm never overrides; no swipe deck, no public like counts, no boosts, no pay-to-win visibility (actually built, not just declared); refundable authorization holds captured only once both sides commit, with correct partial-failure handling; an append-only payment ledger; "prefer not to say" treated as neutral on sensitive questions; policy snapshots that freeze the terms of an already-made commitment.

## Spec-level concerns (from an independent, code-blind review)

A second review read `SPEC.md` alone, without the code or this document, and reached compatible conclusions independently:

- **Zero-human-moderation is the load-bearing risk.** For an app that brokers real in-person meetings and holds money in escrow, this is a bigger bet than for a generic social app, and `minor_suspected`/`unsafe_behavior` reports route through the exact same fully-automated pipeline as spam. See SAF-1 (fixed) and MOD-5/MOD-6 (still open) above.
- **Money that gets captured has no defined destination in the failure paths.** The spec's own text leaves late-cancel money and disputed-date money "retained according to policy" without ever naming the policy, and venue payout is never specified at all. `venueSettlement.service.ts` and `disputeResolution.service.ts` exist specifically because implementers had to invent policy to fill these gaps; both files' own header comments say so.
- **"The algorithm sorts, it never hides" is true in the score dimension and false in practice.** A profile becomes invisible in discovery once its incoming-interest queue or active-conversation count hits its cap, which in practice means the most compatible, most popular profiles are the ones most likely to saturate and disappear. This is a real, capacity-based hiding mechanism sitting in tension with the "we never hide" trust claim repeated three times in the spec.
- **The escrow-as-scam-deterrent argument is probably too optimistic.** The hold is refundable up to 24 hours before the date, so a patient scammer loses nothing; the well-documented romance-scam pattern also mostly stays in-chat and moves off-platform before any real date gets booked, which is a different threat than the low-effort spam the escrow actually deters.
- **Automated moderation has a false-positive/appeal-fairness gap** distinct from the algorithmic-hiding one: a shadowbanned user may not know they've been shadowbanned, and every automated appeal path costs money, a working camera, or time, with no path that involves a human looking at what happened.
- Smaller items: no data-retention periods were specified anywhere in the spec (now addressed in code, see `docs/retention.md`); no accessibility or localization mention in 34 sections (now addressed, see `docs/accessibility.md` and `docs/localization.md`); the §16.2 "score defaults to 0 or neutral" phrasing reads as an unresolved either/or in the spec text itself, not just an implementation detail.
